# Promote product-owner into a repo

Use this when another project needs a local product-owner skill wired to the global one at `~/.agents/skills/product-owner/SKILL.md`.

**How:** open the target repo, paste the prompt below as a single user message, and let the agent run Setup / Promote / Refine-local as appropriate.

**Target shape:** thin local wrapper at `<repo>/.agents/skills/product-owner/SKILL.md` + project constraints in existing `AGENTS.md` / `ROADMAP.md` (or equivalents) — not a second copy of global doctrine.

Do not edit this file into project docs. Do not teach product-owner doctrine here — that lives in `SKILL.md`.

---

## Paste-ready prompt

```
Set up, promote, or refine this repository's local product-owner skill against the global product-owner skill.

## Assumptions

- You already have a developer + SDLC skillset. Do not teach how to code, plan, test, review, or git.
- The global skill is the doctrine source of truth. Read it first; do not restate or duplicate its doctrine in this repo.
- Do not invent golden paths, click budgets, or mental models. Only move or point at what the repo already documents. When Setup needs a home for constraints humans already agreed on, add an empty stub section or `TODO(human)` markers only — never agent-authored path numbers or model lists.

## Read first (mandatory)

1. Global skill: `~/.agents/skills/product-owner/SKILL.md`
2. Promotion notes: `~/.agents/skills/product-owner/PROMOTE.md` (usage notes above this prompt)
3. Discover existing product constraints in this repo, in order of preference:
   - Local skill: `.agents/skills/product-owner/SKILL.md` (or similarly named)
   - `AGENTS.md` (or equivalent agent/product governance doc)
   - `ROADMAP.md` / `CONTEXT.md` / product docs that already hold golden paths, click budgets, or mental models
4. Inventory what is generic judgment vs project-specific (golden-path numbers, preserved/prohibited mental models, product terminology, subsystem names).

## Hard rules

- Keep `~/.agents/skills/product-owner/SKILL.md` domain-agnostic. Never write this project's name, features, or mental models into the global skill unless you are fixing a clear bug in the global skill itself (and then only the bug).
- Do not invent a new documentation scheme. Use this repo's existing conventions for where product constraints, golden paths, and evaluations live.
- Do not duplicate global doctrine in the local wrapper or in AGENTS.md beyond a short pointer / summary the project already uses.
- Prefer the leftmost change that works: Setup → Promote → Refine-local. Pick exactly one primary mode after discovery; you may do a light refine pass after Setup or Promote.

## Modes (pick one primary)

### 1. Setup — no local product-owner yet

Create a thin local wrapper at `.agents/skills/product-owner/SKILL.md` (or this repo's existing skills path if different):

- Frontmatter `name: product-owner`
- `description`: project-aware for local discovery (what this product protects + when to apply) — third-person WHAT + WHEN; include product/domain cues so agents in this repo auto-select it
- Body: apply the global skill; then enforce project constraints from the repo's existing product docs; do not restate global doctrine

Ensure project constraints live where this repo already puts product rules:

- Golden paths / click budgets → `ROADMAP.md` (or existing SoT); if none exist and the repo already uses ROADMAP/CONTEXT-style product docs, add an empty stub / `TODO(human)` section only — otherwise place the stub in the existing product governance doc
- Preserved / prohibited mental models, default surface, simplification hierarchy summary → `AGENTS.md` (or equivalent); use stub / `TODO(human)` when content is missing — never invent the lists
- Point AGENTS (or equivalent) at: canonical global skill + local wrapper as repo entrypoint
- If the repo has an admission / feature gate line (e.g. in ROADMAP), point it at global skill + AGENTS constraints + local wrapper — do not invent a gate if the repo has none
- Do not fabricate path numbers or mental-model lists; leave explicit `TODO(human)` markers when content is missing

### 2. Promote — fat local product-owner full of project-specific doctrine

Extract:

- Generic judgment (mission, doctrine override, golden-path pattern, mental-model pattern, simplification hierarchy, default surface, concept budget, cost-to-value, doctrine check, decision output, gate-as-pattern) → rely on the global skill; delete from the local file
- Project-only golden paths, click budgets, preserved/prohibited mental models, terminology → move into `AGENTS.md` / `ROADMAP.md` / `CONTEXT.md` (or this repo's equivalents), following existing structure

Leave a thin wrapper: apply global doctrine; list pointers to project constraint docs; "Do not restate the global doctrine here."

Update any admission-gate or "primary skill" links to global skill + AGENTS (or equivalent) + local wrapper.

### 3. Refine-local — already points at global skill, but messy / duplicated

- Tighten the wrapper to the thin pattern (pointer + project doc list; no doctrine restatement)
- Dedupe: if AGENTS and the wrapper and ROADMAP all repeat the same doctrine paragraphs, keep numbers/models in product docs and leave only pointers in the wrapper
- Keep the wrapper `description` project-aware for discovery
- Fix broken or stale admission-gate / primary-skill links
- Do not expand scope into unrelated refactors or historical evaluation rewrites

## Target shape (success criteria)

| Artifact | Role |
| --- | --- |
| `~/.agents/skills/product-owner/SKILL.md` | Unchanged (unless fixing a global bug); domain-agnostic |
| `<repo>/.agents/skills/product-owner/SKILL.md` | Thin wrapper: project-aware description + apply global + pointers to project docs |
| AGENTS.md (or equivalent) | Project Product Owner rules: click-budget summary, mental models, pointers to global + local skill |
| ROADMAP / CONTEXT (or equivalent) | Golden-path SoT and/or terminology as this repo already does |
| Admission gate (if any) | Global skill + AGENTS constraints + local wrapper |

## Out of scope

- Rewriting historical product-evaluation docs
- Inventing numbered `docs/<NNN>-…` layouts (or any other scheme) in a repo that does not already use them
- Promoting other skills
- Teaching developer craft or SDLC
- Writing speculative golden paths or mental models "for completeness"

## Done when

1. Local wrapper exists and is thin.
2. Project-specific constraints live in existing product docs, not in the skill body.
3. Global skill has no new project coupling.
4. Links (AGENTS primary skill, ROADMAP admission gate if present) resolve correctly.
5. Report briefly: mode used, files changed, and where golden paths / mental models now live (or which gaps remain for humans).
```
